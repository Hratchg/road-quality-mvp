## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator's local shell → Fly machine | flyctl SSH session — credentials live in `~/.fly/config.yml`; tunnel encrypted via WireGuard but operator-authenticated, not CI-authenticated |
| Fly machine → road-quality-db Postgres | psql runs as `rq` (the application user, full DDL grants on roadquality DB); operator does NOT use postgres superuser |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01-01 | T (Tampering) | migration 004 SQL upload | mitigate | Use SFTP `put` (verifies bytes via flyctl's secure channel); verify with `wc -l` post-upload that line count matches local 59 lines (Phase 9 09-VERIFICATION row 1). |
| T-12-01-02 | D (Denial of service) | live Postgres during DDL | mitigate | LOCKED anti-pattern: `flyctl ssh console -C` keeps psql attached to the DB process tree on the Fly machine itself, sidestepping the wireguard-timeout failure mode that put Postgres into recovery crash loop in v0.3.0 Phase 5 (PROJECT.md line 146). The migration is also small (~1-3s) — even if a transient connection issue happens, IF NOT EXISTS guards make re-run safe. |
| T-12-01-03 | I (Information disclosure) | flyctl ssh logs | mitigate | The DDL contains no secrets; logs captured verbatim into the delta report do not leak credentials. The operator's `~/.fly/config.yml` is local-only; flyctl never echoes the auth token in command output. |
| T-12-01-04 | E (Elevation of privilege) | rq DB user | accept | The `rq` user has DDL grants on `roadquality` DB only. Plan 12-01 does not invoke postgres superuser. The DDL is small and well-tested at Phase 9 (26/26 unit tests + live PG integration confirmed). |
| T-12-01-05 | R (Repudiation) | who applied the migration | mitigate | Operator commits the captured logs under their own git author identity (`git config user.email`); Section 9 sign-off block records timestamp. flyctl SSH logs are server-side traceable to the auth-token issuer. |
