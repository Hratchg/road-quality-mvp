KEY contracts:
- All SQL runs on the SAME `conn` and SAME `cur` so the temp table is visible to the subsequent `pgr_ksp` call (RESEARCH §5 + Pitfall C).
- `DROP TABLE rq_filtered_edges` (NOT `DROP TABLE IF EXISTS`) between attempts — `ON COMMIT DROP` only fires at transaction end, but each attempt's CREATE would otherwise fail with "relation already exists" (RESEARCH Assumption A7).
- The existing `if not paths:` empty-route handling (current routing.py:87-101) is moved to AFTER the 3-attempt chain so it triggers only when all 3 attempts produced zero rows.

## Mock-test compatibility (RESEARCH §7 critical compat note)

Current call sequence per test in test_route.py: `fetchone × 2` (origin, dest snap), `fetchall × 2` (ksp_rows, segment data).

NEW call sequence (best case — attempt 1 succeeds):
- 2 fetchones (snap)
- 1 cur.execute for CREATE_FILTERED_EDGES_SQL (no fetch)
- 1 cur.execute for INDEX_FILTERED_EDGES_SQL (no fetch)
- 1 cur.execute for KSP_FILTERED_SQL → 1 fetchall

- TOTAL: 2 fetchones + 2 fetchalls (same as today!)

The mocks DO need the `_mock_ksp_results()` to be returned on the FIRST fetchall (which is now the filtered KSP — same content, since the mock doesn't care which SQL the cursor was given). No change to the mock data itself.

THE ONE THING TO VERIFY: when MagicMock.execute is called on DDL like `CREATE TEMP TABLE` or `DROP TABLE`, MagicMock just returns a MagicMock — it does not consume from `side_effect` lists tied to fetchone/fetchall. Confirmed by reading test_route.py:_setup_mock_conn — `fetchall.side_effect` is a list, not coupled to execute calls.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP request body (origin/destination lat/lon) → routing.py SQL parameters | Untrusted user input crosses into ST_MakeEnvelope arguments via psycopg2 parameter binding. |
| Operator `ROUTE_FILTER_BUFFER_DEG` env → `bbox_params["buf"]` | Operator-trusted; only readable at module import. |
| 3-attempt fallback chain → connection pool slot lifetime | Each attempt runs on the same pooled connection; on exception the pool's try/finally putconn (db.py:100-101) releases the slot. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-03-01 | T (SQL injection) | `bbox_params` dict-spread → CREATE_FILTERED_EDGES_SQL | mitigate | All 5 keys (`o_lon`, `o_lat`, `d_lon`, `d_lat`, `buf`) bound via psycopg2's named-parameter style. Plan 08-02 Test 6 (`test_create_filtered_uses_named_params`) locks the SQL string. This task uses `cur.execute(SQL, dict)` — psycopg2 escapes/casts. NEVER `.format()` or f-string. |
| T-08-03-02 | D (Resource exhaustion) | A pathological OD pair triggers the wide-filter and full-graph fallbacks back-to-back, consuming up to 3 × 12s = 36s of pool-slot time | mitigate | The 12s `statement_timeout` per query (db.py:97) caps each attempt. Worst case is 36s wall-clock, which is bounded; the pool slot still releases via `try/finally putconn` (Phase 5 SC #9). The route_cache (cache.py:14, TTL=120s) fronts the request — a malicious payload that hits the same OD pair twice gets the cached response on the second hit. Acceptable given no new auth surface and the existing rate-limit is the demo's general request volume. |
| T-08-03-03 | T (Tampering) | An attacker passes degenerate origin == destination, triggering 3 attempts that all return zero rows → finally returns "No route found" | accept | Returning empty response with warning is the correct behavior. Same as pre-Phase-8 for far-apart unreachable points. |
| T-08-03-04 | I (Information disclosure) | Failed attempt 1 leaves `rq_filtered_edges` populated; attempt 2's `DROP TABLE` fails if the table is gone for some reason | accept | `DROP TABLE` (without IF EXISTS) raises if the table is missing — surfaces as 500. This is louder than silently retrying with stale state. RESEARCH Assumption A7 — `ON COMMIT DROP` only fires at transaction end, so within the same `with` block the table persists across attempts. |
| T-08-03-05 | E (Elevation of privilege via DDL) | The route handler now runs CREATE TEMP TABLE — a DDL operation — on a user-facing endpoint | accept | TEMP TABLE creation is in `pg_temp_<N>` (per-connection schema). It is NOT a write to a shared schema. The DB user `rq` already has `CREATE TEMPORARY TABLES` privilege (PostgreSQL default for non-superuser DB owners). No new privileges granted. |
